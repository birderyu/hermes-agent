# 2026-10-23 升级到 v0.22.4

## 为什么

官方 10-21 连发 v0.22.3 和 v0.22.4。v0.22.3 是自 v0.22.2 以来约 620 个 PR、2,911 个非合并提交的汇总（完整说明随 v0.23.0），v0.22.4 在其上修了 14 个提交（桌面 App 的建议胶囊、无依赖插件跳过依赖确认等）。关键是 v0.22.3 把 v0.22.1 里那套网关运行时正式带了回来：`hermes_state*.py` 又有 `session_admissions` 账本表，`gateway/session_authorities.py`、`session_api.py`、`session_api_turn.py`、`api_server_runs._admit_run_to_authority` 都在。所以这次是向前更新，更新器的防降级检查不会拦；v0.22.1 期间留下的 76 条账本记录也重新被认识，那些会话又能删除和清理。

预检：`main`（v0.22.2）是 v0.22.4 的祖先，v0.22.4 在 `upstream/main` 上，标签对象与官方一致。

## 变基

- 31 个提交全部重放。execution_id 补丁干净套上。投递重试补丁只在 `cron/delivery_queue.py` 冲突：v0.22.4 的这个文件与 v0.22.1 逐字节相同（`cron/delivery_outcome.py` 也回来了），所以直接用回 10-15 在 v0.22.1 上做好、测过的版本（`71cfa6f80a`，`recover_abandoned` 同时保留上游的 `fenced`/`settle_quietly` 回写和本补丁的认证重试恢复），没有写新代码。
- `cron/scheduler_delivery.py` 自动合并；相对 v0.22.4 只多出 execution_id 那一行（`_live_route_metadata`）和三处挂点（`_live_send_text`、`_deliver_standalone`、`_deliver_result`）。
- 相对 v0.22.4，`custom/` 之外只有两个 cron 补丁的 4 个文件；`custom/` 与 `c44d686036` 相同；`git diff --check` 通过。

## 测试

v0.22.4 的 `uv.lock`、`pyproject.toml` 变了，按新锁文件在隔离环境里重建测试环境；运行环境的 `~/.hermes/tools`、`~/.local/bin/hermes` 未改动。

| 范围 | 结果 |
| --- | --- |
| `tests/cron/` + `tests/gateway/test_api_server_runs*.py` | 167 个文件，1,562 passed、0 failed、11 skipped |
| 全量 `scripts/run_tests.sh -j 8` | 6,569 个文件，65,096 passed、181 failed、1,836 skipped，2,877.8 秒；`tests/gateway/test_replace_ownership_guard.py` 首次失败、重试通过；失败分布在 65 个文件，没有一个在 `tests/cron/` |
| 65 个失败文件在纯 v0.22.4 副本复跑 | 1,471 passed、166 failed、63 skipped；166 项共同失败，官方单侧 0 项，custom 单侧 21 项 |
| custom 单侧 21 项所在的 9 个文件（与官方逐字节相同），单 worker 复跑 | 搜索、网关守卫、会话库维护等 6 个文件全部通过（并发竞态）；`test_local_component_jobs.py`、`test_local_models_routes.py`、`tests/pm/test_worker.py` 仍有失败，在纯 v0.22.4 上单独跑是同样的用例（暂停/恢复下载一类计时敏感测试） |

结论：没有发现可复现的 custom 新增回归。全量测试前后网关是同一个进程，没有碰到运行中的网关。全量测试在工作副本当前目录留下了一个 `owned/` 目录（官方某个测试生成的 Hermes 主目录骨架，未写 `~/.hermes`），已删除，未提交。

## Ollo 侧

设计会话对升级副本跑 `check.sh --candidate`：708 项全过，0 失败 0 跳过，其中会话权威集成测试 26 项；日历助手构建、签名、自检通过；用升级副本自己的 MCP 客户端连本机假网关，发现并调用 `mcp__ollo__gtd_today`。bridge 在 v0.22.4 上走 canonical 分支。

10-16 那种 409 不会再出现（读代码核对）：v0.22.4 `gateway/session_api.py` 的 `bind_api_steps` 遇到已有 `gateway.api.binding.v1.<会话>` 绑定记录的会话直接放行，只有带了不一致的声明键才冲突；线上 Ollo 会话有这条记录、会话键已是路由格式，Ollo 网关又一直显式带 `session_id`。另外上游在 v0.22.3 正式修了那个问题（#139835）：旧版写在会话行上的声明键，调用方带同一个键来时会被认领并迁到路由。

部署顺序（与设计会话约定）：先单独部署 v0.22.4，插件和 `config.yaml` 都不改；验收通过、`compat.toml` 更新到最终提交后，再部署 Ollo 能力第 2 步。
