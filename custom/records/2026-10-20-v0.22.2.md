# 2026-10-20 升级到 v0.22.2，清理插件提交

## 为什么

官方在 v0.22.1 发布当天（10-15 下午）发了 v0.22.2，发行说明写明：「v0.22.1 was built from the wrong commit. It shipped unreleased gateway work … 0.22.2 is the release 0.22.1 was meant to be.」已知问题：「Sessions that ran under the 0.22.1 gateway can't be deleted in 0.22.2.」10-15 升级时查版本的时间早于它发布，所以错过了。我们部署的正是这个错误的构建：10-16 的 Ollo 409（会话权威 API 绑定）和 ollo-bridge 为它做的 canonical 身份适配，针对的都是这批未发布的网关改动。v0.22.2 另修了受 launchd 等监管的网关在重启后可能起不来的问题。

v0.22.2 由 `release/0.22.1` 重新发布，挂已发布的 v0.22.1 作父提交（`d923a5eb48`「Release 0.22.2 from release/0.22.1 with the published v0.22.1 as a parent」），所以 `main` 能快进，但代码上撤掉了 v0.22.1 里的未发布改动：v0.22.1 → v0.22.2 删掉了 `gateway/session_api.py` 的 227 行，`api_server_runs.py` 改 284 行，`cron/scheduler_delivery.py` 改 313 行。预检：`main`（v0.22.1）是 v0.22.2 的祖先，v0.22.2 在 `upstream/main` 上。

## 变基

1. **全部重放到 v0.22.2**。execution_id 补丁干净套上；投递重试补丁在 `cron/delivery_queue.py` 的 `recover_abandoned()` 冲突：v0.22.1 版本里有上游的 `fenced` 列表和 `settle_quietly()` 回写，v0.22.2 没有。核对发现 v0.22.2 的 `cron/delivery_queue.py` 与 v0.21.6 逐字节相同，`cron/delivery_outcome.py` 不存在，所以队列部分直接用回原补丁（10-11 在 v0.21.6 上写好、测过的 `1bbb986596` 版本），没有写新代码。`scheduler_delivery.py` 自动合并，结果等于原补丁版本加上官方几处写法整理（类型标注、去掉 `noqa`、`encode()`）；execution_id 仍在 `_live_route_metadata` 的普通分支。`cron/delivery_retry.py`、`tests/cron/test_delivery_retry.py`、`cron/delivery_queue.py` 与原补丁逐字节相同。
2. **剥掉插件历史**：按 [补丁清单](../patches.md) 写好的办法，`git filter-branch --index-filter 'git rm -r -q --cached --ignore-unmatch hermes-plugins' --prune-empty -- v0.22.2..HEAD`，36 → 30 个提交，`hermes-plugins/` 以外与剥离前完全一致。
3. **丢掉 3 个只改 `.gitignore` 的提交**（插件迁入、删 hermes-plus 例外、删除 `hermes-plugins/`），三者净效果为零：30 → 27 个提交，`.gitignore` 与 v0.22.2 一致。
4. **改标题**：7 个原插件提交剥离后只剩 `custom/records/` 的记录，标题从 `feat/fix(ollo-bridge): …` 改为 `docs(custom): record ollo-bridge feat/fix: …`，正文注明插件代码已在 Ollo 仓库，原正文保留。

结果：27 个提交里没有任何提交碰过 `hermes-plugins/`；`custom/` 与 `5feee4e3ef` 完全相同；相对 v0.22.2，`custom/` 之外只有两个 cron 补丁的 4 个文件；`git diff --check` 通过。

## Ollo 侧的兼容

设计会话只读核对发现，ollo-bridge 在函数里延迟导入了只在 v0.22.1 才有的模块（`gateway.session_authorities`、`gateway.session_api_turn`、`api_server_runs._run_idempotency_identity`），没有兜底；直接升到 v0.22.2，确认工具和 `/v1/runs` 的请求处理都会出错。Ollo 仓库把它们改成「有就用，没有就走旧路径」，测试同时覆盖两个版本，`check_host` 加了可选项。在升级副本 `52877119c2` 上跑 `check.sh --candidate`：27 个必需宿主符号和 execution_id 元数据都在，可选能力都不在、走旧分支，原插件测试 466 项、合计 562 项全过；同一份代码对 v0.22.1 默认模式也通过。改之前的版本对同一副本有 19 个失败、26 个错误，全是缺少上述模块。

部署顺序：旧插件不能在 v0.22.2 上运行，新插件同时兼容两个版本。Ollo 的部署工具要求网关停下（同步会改 `jobs.json` 里的任务提示词），所以按：停网关 → Ollo `manage.py backup/sync --quiesced` → `hermes update --branch custom` → 启动网关 → 核对 → Ollo `verify --send` 和一次真实确认写入。

## 部署

**备份**（`~/.hermes/backups/pre-v0.22.2-20261020/`，79 MB）：运行目录分支 `backup/custom-pre-v0.22.2-20261020`（`b91c8e5a9c`）；`config.yaml`、`.env`（只复制）、LaunchAgent、`~/.local/bin/hermes`、`cron/jobs.json`；6 个主数据库与 6 个档案的 `state.db`（在线备份，完整性检查均 ok）。Ollo 的部署工具另有备份（`~/.ollo-hermes-backups/s2-first-deploy-20261020-1019*`）。

**第一次尝试（10:19–10:21）**：10:19:14 `hermes gateway stop`（launchd 卸载服务，进程退出，状态 stopped，无进行中的任务）→ 设计会话 `manage.py backup/sync --quiesced`（第一次从 Ollo 仓库 `hermes/` 部署：插件兼容 v0.22.2 的 3 个文件和 `schema.json`；112 个旧的非运行文件清掉；两份技能、四个采集脚本、日历助手、四段任务提示词本就一致；`verify` 0 差异）→ 10:20:19 `hermes update --branch custom --yes` 被拒：

> ✗ Refusing to move this install to origin/custom: that release predates the gateway runtime these session stores now use. Downgrading is unsupported.

更新器没有动代码。按回滚方案 10:20:49 `hermes gateway start`，网关回到 v0.22.1（`b91c8e5a9c`）加新插件（新插件同时兼容 v0.22.1），LaunchAgent 仍经 `osascript`、plist 与备份一致；设计会话 `verify --send` 真实收发通过。Ollo 中断约 2 分钟。

**原因**（`hermes_cli/update_downgrade_guard.py`）：只在三个条件同时成立时拒绝：目标不是当前 HEAD 的后代；目标的 `hermes_state*.py` 没有 `session_admissions` 建表语句（没有运行时账本）；某个档案的 `state.db` 已有账本记录。主档案有 76 条 `session_admissions`（v0.22.1 的会话权威写入），其他档案为 0。官方用户从 v0.22.1 升 v0.22.2 时，v0.22.2 是 v0.22.1 的后代，按向前更新放行，代价就是发行说明的已知问题：这些会话在 v0.22.2 里删不掉、也清理不了（账本表 `ON DELETE RESTRICT`）。我们被拒，只因为变基后的 `custom` 不是运行目录旧 HEAD 的后代。等 v0.23 带回运行时，就又是正常的向前更新。

**用户选择手工对齐**（等同官方的向前更新路径，接受上述已知问题；会话自动清理本来已关）。11:04:23 停网关 → `git -C ~/.hermes/hermes-agent reset --hard origin/custom`（`9c2353bd82`；旧 `hermes-plugins/` 随之删除，无残留）→ 11:04:47 `hermes update --branch custom --yes`：显示 `Already up to date`，补完 TUI、网页、桌面 App 的重建以及技能与配置检查，并自行重启网关。新旧 `custom` 的依赖锁文件相同，pm 环境没有换代。
