## 发行版

[v0.21.6](https://github.com/NousResearch/hermes-agent/releases/tag/v0.21.6)（2026-10-08）是官方新发布流水线出的第一个版本，标签命名从 `vYYYY.M.D` 改为 `vX.Y.Z`；与 v0.21.5 之间有 8,867 个非合并提交、约 2,100 个 PR，完整说明要等 v0.22.0。预检：`f97608f178` 是标签的祖先，标签可从 `upstream/main` 到达。`rc.*`、`*+canary.*` 标签不是发行版。

和本 fork 相关的变化：

- **安全修复**：dashboard 登录限流可被伪造 `X-Forwarded-For` 绕过等四项；自动 git 调用可能执行不受信仓库配置的 filter 程序；邮件网关发件人校验。这是这次升级的主要理由。
- **依赖改由 `pm` 管理**：工具在 `$HERMES_RUNTIME_DIR`（默认 `~/.hermes/tools`），环境在 `$HERMES_HOME/installs/`；不能再用裸 `pip`/`uv` 改环境。开发环境因此要隔离，见 [维护方式](../maintenance.md#开发环境)。
- **用户语言覆盖层**：`$HERMES_HOME/locales/<语言>.yaml` 可以覆盖内置文案。
- **任务事件流**：`/v1/runs/{id}/events` 改为带序号的 `_RunStream`，支持多订阅、保留最近 1000 个事件、按 `Last-Event-ID` 续传；仍在内存里，进程重启即丢。
- **Photon**：上游已展开 iMessage `reply`、丢弃 `read`/`read_receipt`，并把 sidecar 依赖固定在 `spectrum-ts 12.7.0`。
- 插件默认仍在网关进程内运行（`plugins.isolation: in_process`）；Ollo 插件用到的钩子与接口都还在。

## 部署

**预检与备份**（`~/.hermes/backups/pre-v0.21.6-20261011/`）：`config.yaml`、`.env`（只复制）、LaunchAgent、`~/.local/bin/hermes`、`plugins/`、`cron/jobs.json`、旧 `venv`（679 MB）、6 个数据库（SQLite 在线备份，完整性检查均 ok）、Ollo 两个插件的数据库；运行目录建回退分支 `backup/custom-pre-v0.21.6-20261011`（`309821b2e1`）。无进行中的任务。Hermes 桌面 App 从 10-01 起一直开着，后端跑在旧 `venv` 上，部署前正常退出，没有重新打开。语言覆盖文件复制到 `~/.hermes/locales/`。

另外发现：全量测试进行中（07:34）网关被测试发了 SIGTERM，launchd 将其拉起，并向 iMessage 发了一条关机通知；见 [维护方式](../maintenance.md#测试与基线对照)。

**第一次 `hermes update --branch custom --yes`（0.21.5 的更新器）出了问题**：

1. 旧更新器正确地把 `custom` 对齐到 `origin/custom`（旧 HEAD 存到 `refs/hermes-update-backups/diverged-custom-…`），然后把后半程交给新代码。
2. 交接中 `--branch custom` 丢失，新代码按「更新通道 main」执行：认为检出「停在」`custom` 上，按 `updates.auto_switch_parked_branch`（默认开）切到 `main`。
3. 因为运行目录配了 `upstream` 远端，又把 `main` 快进到官方开发主线 `b65cd56cfc`（比 v0.21.6 多 606 个提交），并 `push origin main` 推到了 fork。
4. 按 `b65cd56` 装依赖、重写 LaunchAgent、重启网关，重建 TUI、网页界面和桌面 App；配置按官方迁移升到版本 50。
5. 旧更新器最后发现检出在 `main`，报「not claiming success」退出。此时网关跑的是 `b65cd56`，不含本 fork 的补丁。

**修复**：

- `git checkout custom`，本地 `main` 退回 `818c13be1d`；
- 删除运行目录的 `upstream` 远端，`hermes config set updates.auto_switch_parked_branch false`；
- 用新版更新器再跑 `hermes update --branch custom --yes`：补完上次欠下的步骤，网关在 `67d3c0b3` 上重启；
- 已是最新提交时更新器不再同步依赖，又跑 `hermes pm install`（按 `custom` 的 lockfile；与 `b65cd56` 只差 `nemo_relay`，以及只影响 Termux 的工具锁）和 `hermes gateway restart`；
- 运行目录里旧的未跟踪文件 `cron/scheduler_delivery.py.hermes-plus-inbox.bak` 移进备份目录，检出恢复干净。

配置迁移（33 → 50）是 v0.21.6 自身的标准迁移：`delegation.max_iterations` 50 → 250、`display.background_process_notifications` all → concise、Home Assistant 移出核心后自动启用 `homeassistant` 插件。

**遗留**：fork 上的 `main` 被推成了 `b65cd56`，需要用 `--force-with-lease` 推回 `818c13be1d`（同样要用户本人执行）。

## 升级带来的权限回退

09:30 的「GTD-今日安排-周末」按时触发、09:32 完成，但报告写的是「受权限限制」：读提醒事项和日历都失败，日志为 `Calendar full access is not granted`（`remindctl` 与日历脚本同样）。前一天同一任务正常。

原因：v0.21.6 的 LaunchAgent 改为 `/usr/bin/osascript` 启动网关，用来取得 macOS「本地网络」权限（`hermes_cli/gateway_launchd.py` 的 `launchd_program_arguments`）。这样 macOS 把网关子进程的权限归到 `osascript`，以前授给旧 `venv` Python 的提醒事项、日历权限不再适用。

处理：需要用户在 Mac mini 上给 `osascript` 授予「提醒事项」和「日历（完全访问）」，见 [部署](../deploy.md#4-验证) 的日历与提醒事项一项。授权后再记一次结果。
